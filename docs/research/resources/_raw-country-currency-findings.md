# Raw findings: country and currency, benchmark findings 3-6 (2026-11-08)

**Scope:** benchmark findings 3 (withdrawn codes with several successors), 4 (English country-name variants), 5 (INVALID currency, no error row), 6 ("$5" with no country).
**Verification:** URLs below were fetched in this session; claims come from the fetched text, which was often truncated (noted per entry). Local facts were computed read-only with `.venv/bin/python -I` (babel 2.18.0, pycountry 24.6.1) and by reading the repo files. Anything not fetched is marked "not checked". No repo file was edited.

## Diagnosis from the code (read-only)

D1. `country_codes.py::_SINGLE_SUCCESSOR_ALIASES` is built from `babel.core.get_global("territory_aliases")`, keeping only entries with one successor. Computed values (CLDR via babel 2.18.0):
`SU -> RU AM AZ BY EE GE KZ KG LV LT MD TJ TM UA UZ` (15), `CS -> RS ME`, `AN -> CW SX BQ`, `YU -> RS ME`, `NT -> SA IQ`, `DD -> DE`, `ZR -> CD`, `TP -> TL`, `BU -> MM`, `FX -> FR`, `YD -> YE`, `VD -> VN`.
So single-successor codes (DD, ZR, TP, BU, FX, YD, VD) resolve; SU, CS, AN, YU, NT do not, and `country.py::_unresolved` gives INVALID.
D2. `pycountry.historic_countries` (ISO 3166-3 data) has 4-letter codes: `SUHH USSR 1992-08-30`, `CSHH Czechoslovakia 1993-06-15`, `CSXX Serbia and Montenegro 2006-09-26`, `ANHH Netherlands Antilles 2010-12-15`, `YUCS Yugoslavia 2003-07-23`, `DDDE`, `ZRCD`, `TPTL`, `NTHH Neutral Zone`. It has no successor list, only a `comment` on some rows.
D3. **CS is two different countries.** `CSHH` (Czechoslovakia, successors CZ and SK) and `CSXX` (Serbia and Montenegro, successors RS and ME). CLDR/babel list only `RS ME`. Returning RS, or "RS or ME", for a bare `CS` would drop Czechoslovakia: a wrong reading, not only an incomplete one. `YU` similarly was renamed to `CS` (YUCS), not split; babel lists `RS ME` for it.
D4. Current resolver results (run): `The Netherlands`, `Cocos Islands`, `Palestinian Territory`, `Palestine`, `Bonaire, Saint Eustatius and Saba`, `The Gambia`, `Congo (DRC)`, `Netherlands (the)` all give None. `The Bahamas` works (hand table). `Turkey`, `Palestinian Territories`, `Caribbean Netherlands` work. **`Congo` resolves to CG** (pycountry name of CG) although "Congo" also names CD; `Korea`, `Virgin Islands` correctly give None. The `Congo` result is a guess under the project rule; flag to owner.
D5. `scripts/generate_cldr_names.py` documents (ponytail comment): Babel exposes no `alt` names, so CLDR's `short`/`variant` names are missing from `_cldr_country_names.py`. Reading CLDR XML would close the gap.
D6. `money.py::MoneyNormalizer._currency_half`: empty currency text gives `(None, True)`; a bare symbol that CURRENCY will not resolve gives `(None, True)` too ("a known unknown"), so `$5` is NORMALIZED with `currency=None`, `comparison="5"`. ADR-011 says a bare `$` "stays recorded as `original_currency` with `canonical_currency: null` and `currency_confidence: low`, never defaulted to USD" (ADR-011 lines 31-35), and that unparseable-looking numbers are AMBIGUOUS with candidates (lines 25-30). So the app follows ADR-011's text; the benchmark key does not.
D7. `currency.py` docstring: `$`, `¥`, `kr` are dropped at generation time when they mean several currencies. Babel computed over all locales (Locale.currency_symbols, the standard symbol, not narrow): `$` is used by 27 codes (ARS AUD BBD BMD BND BSD BZD CAD CLP COP CUP FJD GYD JMD KYD LRD MXN NAD NZD SBD SGD SRD TTD TWD USD UYU XCD); `¥` by CNY, JPY; `£` by FKP GBP GIP SHP SSP; `kr` by DKK EEK NOK SEK; `R` by ZAR only; `Rs` by INR MUR PKR SCR. In `en`: `$`=USD, `CA$`, `A$`, `MX$`, `HK$`, `NZ$`, `CN¥`, `¥`=JPY, `£`=GBP.
D8. ADR-018: only AMBIGUOUS is queued for review; INVALID "is not a question anyone can answer"; the queue row holds the normalizer's `structured`/`warnings`/`errors`. So candidate readings placed in `structured` reach the reviewer.

## A. Withdrawn codes

1. Unicode — UTS #35 Part 1 Core, Annex C "LocaleId Canonicalization", Territory Exception — https://www.unicode.org/reports/tr35/tr35.html — licence: Unicode Terms of Use (spec text; CLDR data Unicode-3.0, https://www.unicode.org/license.txt, taken from the repo's generated file header) — version/date not seen (page header not in the part read) — Finding: `territoryAlias` is the only alias type with several values, `replacement` is space-delimited; for several values the canonicalizer takes the likely territory of the locale's language (and script) and uses it if it is in the list, otherwise the first value. Example in the spec: `hy-SU` becomes `hy-AM` (AM is not first in the SU list). Older spec versions (tr35-29) said "use the first". Relevance: the rule needs a language to choose; the engine has none for a bare country cell, so the CLDR rule cannot be applied. "Take the first" would silently turn `SU` into `RU` and `AN` into `CW`: a guess. Truncated: only parts of the 312,000-char page were read.
2. Unicode — UTS #35 Part 6 Supplemental, `territoryAlias` — https://www.unicode.org/reports/tr35/tr35-info.html#Supplemental_Territory_Alias — Finding: `reason="deprecated"` (e.g. "CS by RS ME") or `overlong` ("USA" by "US"); no selection rule on this page; points to Part 1. Relevance: CLDR itself treats multi-value as data, and leaves the choice to the caller.
3. Unicode CLDR — `cldr-json` supplemental aliases — https://raw.githubusercontent.com/unicode-org/cldr-json/main/cldr-json/cldr-core/supplemental/aliases.json — licence Unicode-3.0 — Finding (partial, file truncated at ~100k chars): `AN -> CW SX BQ`, `CS -> RS ME`, `BU -> MM`, `DD -> DE`, `FX -> FR`, all `reason: deprecated`. SU, YU, ZR, TP were past the cut; their values are from local babel 2.18.0 (D1), which packages CLDR (version not read; not checked).
4. Wikipedia — ISO 3166-3 — https://en.wikipedia.org/wiki/ISO_3166-3 — licence CC BY-SA 4.0 (page text; not checked on page) — secondary source, ISO's own standard text is paywalled/not read — Finding: four-letter code = old alpha-2 + (new alpha-2 if renamed or merged, `AA` if unchanged, `HH` if divided, `XX` for Serbia and Montenegro). Each entry lists the successor names and codes. Rows: `SUHH` divided (13 states listed; babel lists 15 including RU and BY... count differs, see Open question 3), `CSHH` Czechoslovakia -> CZ, SK; `CSXX` Serbia and Montenegro -> ME, RS; `ANHH` -> BQ, CW, SX; `YUCS` renamed to CS; `DDDE` merged into DE; `ZRCD` renamed CD; `TPTL` renamed TL. A deleted alpha-2 is "transitionally reserved" for at least 50 years; CS was deleted twice (reused). Relevance: ISO 3166-3 is the authoritative successor list and shows `HH` = "no single successor" by design: the standard itself says a divided country has no single successor. It also shows CS needs a date to read.
5. Wikipedia — ISO 3166-1 alpha-2 — https://en.wikipedia.org/wiki/ISO_3166-1_alpha-2 — CC BY-SA 4.0 (not checked on page) — partial read (truncated at 100k of 137k chars) — Finding: newer stability policy says withdrawn codes "should no longer be reassigned" (CS is the cited reuse); user-assigned ranges AA, QM-QZ, XA-XZ, ZZ; real-world use of `XK` (Kosovo), `XA`, `XI`. Relevance: an alpha-2 can be a withdrawn code and a current code in different eras (BQ: `BQAQ` British Antarctic Territory in pycountry, and Bonaire now). Dates are the only disambiguation.
6. pycountry — `historic_countries` (ISO 3166-3) — https://github.com/pycountry/pycountry — LGPL-2.1 (not checked on page; recall) — installed 24.6.1 — computed (D2). Fields: `alpha_4`, `alpha_3`, `name`, `withdrawal_date`, optional `comment`. No successor field.
7. Babel — `territory_aliases` — https://babel.pocoo.org/ — BSD-3-Clause (not checked) — installed 2.18.0 — computed (D1): `dict[str, list[str]]`, preserves multi-value lists.
8. Other libraries' behaviour with multi-successor codes (ICU, `country_converter`, Java `Locale`, Node `Intl.getCanonicalLocales`): **not checked**. Only the CLDR rule (1) is verified.

### Presenting candidates to a reviewer
Not a standard. Grounded in the repo: ADR-011 records "both candidate interpretations" for AMBIGUOUS numbers; ADR-018 stores the normalizer's `structured` in the queue row. So one reading per successor in `structured` (e.g. `candidates: [{alpha2, name}, ...]`) fits existing practice. Unverified design; owner decides.

### Options for finding 3
- **3a. AMBIGUOUS, candidates = the CLDR successor list (`SU`: 15, `AN`: 3, `CS`: RS+ME, `YU`: RS+ME).** Pros: one general rule from data (all multi-value babel entries), reviewer sees all readings, no dictionary to maintain. Cons: for `CS` the list is incomplete (Czechoslovakia: CZ, SK absent from CLDR); for `NT`, `YU` the semantic is odd (YU was renamed, not divided). Risk of wrong value: low for status (abstains); the candidate list itself can mislead a reviewer on CS.
- **3b. AMBIGUOUS for these codes with candidates from ISO 3166-3 (pycountry `historic_countries` joined by alpha-2 prefix: all `CS*`, `SU*` rows give successors by name).** Pros: authoritative, shows CS as two historic countries (CSHH, CSXX), dated. Cons: pycountry has no successor codes, only the old country name and date; mapping to successors needs the Wikipedia/ISO text or a hand table (violates the "no hand table" rule), so candidates would be historic countries, not today's alpha-2. Risk: none of a wrong value; reviewer sees the real history.
- **3c. Keep INVALID.** Pros: no change. Cons: a real, once-valid code is reported as garbage; INVALID is never queued (ADR-018), so no human ever sees it. Risk: none of a wrong value, but silent loss.
Recommendation: **3b for the status and reading, 3a for the candidate list where CLDR has one: AMBIGUOUS, with structured readings = the ISO 3166-3 historic entries (name, dates) plus the CLDR successor codes when present, flagged `source`.** Minimum viable: 3a plus a flag when pycountry has more than one `alpha_4` starting with the code (CS, BQ), so CS never shows RS+ME as the only reading. Never pick a single successor.

### Open questions for the owner (finding 3)
1. Is a code that is also a current code (BQ) in scope? Today it resolves to Bonaire; the history is a different question.
2. Should YU (renamed to CS, then divided) and NT (SA or IQ) be AMBIGUOUS as well? Same rule: any multi-value or non-unique code.
3. SU has 15 successors in babel; the Wikipedia ISO 3166-3 row lists 13 ("from Armenia to Uzbekistan"; the exact list was not read). Which list is authoritative, and is it acceptable to show CLDR's list?
4. Is the reading shape (`candidates` in `structured`) acceptable to the review queue, or does the queue need a field?

## B. English country-name variants

9. GeoNames — countryInfo.txt — https://download.geonames.org/export/dump/countryInfo.txt — licence: the export page https://www.geonames.org/export/ states "cc-by" and asks for credit; version of CC BY not stated on the page read; the file itself carries no licence text; the page does not name countryInfo.txt — Finding (fetched, current at fetch time): `NL The Netherlands`, `CC Cocos Islands`, `PS Palestinian Territory`, `BQ Bonaire, Saint Eustatius and Saba`, `CD Democratic Republic of the Congo`, `CG Republic of the Congo`, `KR South Korea`, `KP North Korea`, `GN Guinea`, `GQ Equatorial Guinea`, `GW Guinea-Bissau`, `VG British Virgin Islands`, `VI U.S. Virgin Islands`, `BS Bahamas`, `GM Gambia`, `VA Vatican`. One name column only. Relevance: confirms all four benchmark names come from GeoNames. A source with attribution duty (CC BY) must not be vendored without a licence check (B6 does not forbid, but see Open question).
10. Unicode CLDR — `common/main/en.xml` — https://raw.githubusercontent.com/unicode-org/cldr/main/common/main/en.xml — Unicode-3.0 — main branch at fetch time (version not read); only the first 100k of 483k chars were read, and the territories block was reported fully visible — Finding: standard names `NL Netherlands`, `CC Cocos (Keeling) Islands`, `PS Palestinian Territories`, `BQ Caribbean Netherlands`, `CD Congo - Kinshasa`, `CG Congo - Brazzaville`. Alternates: `CC alt=short "Cocos Islands"`, `PS alt=short "Palestine"`, `CD alt=variant "Congo (DRC)"`, `CG alt=variant "Congo (Republic)"`, `GB alt=short "UK"`, `US alt=short "US"`, `TR alt=variant "Turkey"`, `CZ alt=variant "Czech Republic"`. No alternate for `NL`, `BQ`, `KR`, `KP`, `GM`, `BS`, `VA`, `MK`. Relevance: CLDR `en` lists **"Cocos Islands"** and **"Palestine"** (authoritative, general fix); it does not list "The Netherlands", "Palestinian Territory" or "Bonaire, Saint Eustatius and Saba". Reading the XML closes the gap the generator comment (D5) names. Whether other locales' `alt` entries are just as safe: not checked.
11. ISO 3166-1 short names — https://www.iso.org/obp/ui/#iso:code:3166:NL (OBP, JS page; **not opened**) — ISO terms, data not freely redistributable (not checked) — Finding via search snippet only: ISO short name is "Netherlands (the)" (and "Netherlands Antilles (the)"); Wikipedia says ISO 3166-1 names come from the UN Terminology Bulletin *Country Names* and UNSD M49 (secondary, from search; not checked directly). Relevance: the ISO/UN convention puts the article in trailing parentheses, so "(the)" is a recognised pattern, but "The Netherlands" with a leading article is not any standard's form. pycountry (`name`, `official_name`, `common_name`) returns None for `Netherlands (the)` and `Bahamas (the)` (run).
12. UN M49 / UNTERM — https://unterm.un.org/unterm2/en/country — the page text fetched was empty (JS); **not checked**: whether UNTERM lists "the Netherlands", "Netherlands (Kingdom of the)", or the licence. Same for CIA World Factbook "conventional short form" (public-domain claim, not checked) and Wikidata labels/aliases (CC0 claim from general knowledge, not checked in this session).
13. Leading-article stripping — **no standard found.** Neither the CLDR en data read (10) nor ISO's trailing "(the)" (11, snippet) defines stripping a leading "The". CLDR UTS #35 lenient parsing is about numbers/dates/punctuation; applicability to names not checked. The repo already hand-lists `the bahamas` (`_KNOWN_NON_ISO_ALIASES`), which is the one-at-a-time table the project rejects.
14. Names that are themselves ambiguous (computed or from 9/10): "Congo" (CG vs CD; CLDR says `Congo - Brazzaville` / `Congo - Kinshasa`, plus variants "Congo (Republic)", "Congo (DRC)"); "Korea" (KR vs KP); "Guinea" is GN's own name but also a prefix of GQ and GW; "Virgin Islands" (VI vs VG); "Georgia" (GE; also a US state, not a country ambiguity); "Niger" (NE vs NG, different words); "Samoa", "Sudan" (SD vs SS, name stable), "Micronesia" (FM, also a region: not checked). **Current engine gives `Congo` -> CG, a guess to review.**

### Options for finding 4
- **4a. Read CLDR `en` (and other locales') `alt` names from the CLDR XML in `generate_cldr_names.py`, and drop names shared by several codes.** Pros: authoritative, general, closes a documented gap, fixes "Cocos Islands" and "Palestine" (and "Turkey", already works). Cons: does not fix "The Netherlands", "Palestinian Territory", "Bonaire, Saint Eustatius and Saba". The generator must add a second data source (XML, not Babel). Risk of a wrong value: low if clashes are dropped as today; a shared alt such as "Congo" must be dropped, or the existing CG guess becomes a CLDR-backed guess.
- **4b. Add GeoNames `countryInfo.txt` names (CC BY) as another generated table with the same "drop names shared by several codes" rule.** Pros: covers all four benchmark names; a published, maintained list; same generator pattern. Cons: attribution duty and a new data source (needs a yes, B6/F7); the benchmark expected values come from GeoNames, so the gain on that corpus is partly circular (C2: not tuning to the test DB). Risk: low; GeoNames names are one-to-one with codes.
- **4c. Strip a leading "The " before lookup (only the word at the start, only when the rest resolves exactly).** Pros: tiny, helps "The Netherlands", "The Gambia". Cons: no standard backs it; ISO convention is trailing "(the)"; a name that begins with "The" and is a different country is unlikely but not checked (e.g. none in pycountry names, not checked by run). Risk: low; but is a rule, not authoritative data. Also support trailing ", the"/"(the)" if wanted.
Recommendation: **4a first (authoritative), then 4c narrowly (leading "The" and trailing "(the)", exact match of the rest only, never followed by fuzzy matching).** 4b only after the owner decides on CC BY. Fix `Congo` independently: it is a wrong-value risk today, found in this research, not in the benchmark. For the four benchmark names: "Cocos Islands" (4a), "The Netherlands" (4c), "Palestinian Territory" and "Bonaire, Saint Eustatius and Saba" stay unresolved without 4b or a hand entry.

### Open questions for the owner (finding 4)
1. Is GeoNames (CC BY 4.0 per its export page; version not checked) an accepted data source, with an attribution line in the docs?
2. Is stripping "The" accepted as a rule, given no standard says so? Or only the data route?
3. Should `Congo` be AMBIGUOUS (CG or CD)? It resolves to CG today.
4. "Palestinian Territory" and the spelling "Saint" vs "Sint": accept as spelling variants of the same name only if a source lists them; none of the sources read does except GeoNames.

## C. Currency symbols and "$5"

15. Unicode CLDR — currency symbol data — https://www.unicode.org/reports/tr35/tr35-numbers.html#Currencies — Unicode-3.0 — **not fetched in this session.** From the local babel 2.18.0 data (D7): the standard symbol `$` appears in 27 currencies across locales; `¥` in 2; `£` in 5; `kr` in 4; `R` in 1. CLDR also has a "narrow" symbol (`alt="narrow"`) — in CLDR a narrow symbol is meant for tight space and is itself ambiguous (`$` for many); babel's `Locale.currency_symbols` does not expose it, **not checked** which currencies use `$` as narrow.
16. Babel — `parse_decimal` — https://babel.pocoo.org/en/latest/api/numbers.html — BSD-3-Clause (not checked) — 2.18.0 — run: `parse_decimal('$5','en_US')` and `parse_decimal('5 USD','en_US')` both raise `NumberFormatError`. Babel does not parse money; currency is separate.
17. price-parser (Scrapinghub/Zyte) — https://github.com/scrapinghub/price-parser — BSD-3-Clause (README) — latest version not seen — `Price.fromstring("Price: $119.00")` returns amount `Decimal('119.00')` and `currency='$'`: the symbol as written, not an ISO code; `Price.fromstring("50")` returns the amount with no currency. Relevance: a known tool returns the amount and the raw symbol, and leaves the code to the caller. This is "amount known, currency unresolved".
18. py-moneyed — https://pypi.org/project/py-moneyed/ — BSD — 3.0, 2022-11-27 — `Money` is built with an amount and a currency; whether a Money with no currency is allowed and what an unknown code does: not stated on the page, **not checked**.
19. HL7 FHIR R5 — Money datatype — https://hl7.org/fhir/datatypes.html#Money — CC0 (not checked; HL7 states FHIR is CC0 elsewhere) — v5.0.0 — `value` is `decimal [0..1]`, `currency` is `code [0..1]` bound at Required strength to ISO 4217. Neither is required, so the standard allows an amount with no currency. Page truncated; Money-level invariants not confirmed. Relevance: the one standard read allows "amount known, currency absent".
20. ISO 20022 amount types (ActiveCurrencyAndAmount) — **not checked.**
21. libaddressinput / libphonenumber analogy — **not checked** (not fetched; not needed for the answer).

### Options for finding 6
- **6a. As now: NORMALIZED, amount 5, currency empty.** Pros: matches ADR-011 text and price-parser/FHIR practice (amount without currency is representable); no guess; the amount is right. Cons: a downstream user can read "5" as plain 5 with no sign the currency was lost (status NORMALIZED); not queued for review (only AMBIGUOUS is). The benchmark key expects AMBIGUOUS. Risk of a wrong value: low in the engine, medium downstream (the symbol is dropped from `comparison`).
- **6b. AMBIGUOUS, candidates = codes that use the symbol in CLDR (for `$`: 27).** Pros: queued (ADR-018), reviewer sees the amount and the readings, matches the benchmark key and the "never guess" rule. Cons: the candidate list is long and low value; the amount `5` is the same in every reading, so the question being asked is only the currency. The amount is lost to a reader unless kept in `structured`. Risk: none of a wrong value.
- **6c. NORMALIZED amount with a currency sub-status "AMBIGUOUS" (e.g. `structured.currency_status`, candidates listed, `comparison` carries the amount and a marker).** Pros: keeps the amount for numeric work, still marks the gap, no status change. Cons: the engine has no sub-status field today; every consumer must read it; ADR-018 queues only top-level AMBIGUOUS. Risk: consumers ignoring the sub-status read the value as a plain number (silent). 
Recommendation: **6b, with the amount preserved in `structured` and candidates taken from CLDR (the same data `currency.py` already uses to drop `$`).** Reason: a normalized value that is later joined on `comparison` must never look complete when a currency was stated but not resolved; abstaining costs one review row. If the owner wants to keep today's behaviour, document it as an ADR-011 decision, because the benchmark key and the ADR-018 queue disagree with it. Distinguish the empty-currency case (`5`, no symbol: NORMALIZED, as FHIR allows) from a stated-but-unresolved symbol (`$5`).

### Open questions for the owner (finding 6)
1. Is "currency stated but not resolved" a different case from "no currency stated"? `5` stays NORMALIZED; `$5` becomes AMBIGUOUS.
2. Candidate list: all CLDR codes for the symbol (27), or none (just a flag)?
3. Does a context hint (column country, locale) resolve `$5` as ADR-011 says? Unchanged; this is only the no-context case.
4. Should ADR-011 be amended to say "AMBIGUOUS" instead of "canonical_currency: null"?

## D. Invalid code values in data-quality tools, and ISO 4217

22. Great Expectations — result format — https://docs.greatexpectations.io/docs/reference/learn/expectations/result_format/ — Apache-2.0 (not checked) — version not seen — For column-map expectations (e.g. `expect_column_values_to_be_in_set`) each row is evaluated; `unexpected_count` is a count, `partial_unexpected_list` a sample capped at 20, `unexpected_list` and `unexpected_index_list` (row ids by key columns) only in `COMPLETE`. The expectation page itself (https://greatexpectations.io/expectations/expect_column_values_to_be_in_set) had no body text.
23. Soda — validity metrics — https://docs.soda.io/soda-cl/validity-metrics.html — Apache-2.0 for Soda Core (not checked) — Values are sorted into missing, invalid or valid; counts sum to the row count. `valid values`/`valid format` mark the rest invalid. Failed-row samples default to 100 (Soda Cloud).
24. Deequ — https://github.com/awslabs/deequ — Apache-2.0 (README) — release not seen — `isContainedIn("priority", Array(...))` is a constraint that fails the check; the README does not say whether it returns row-level violations. DQDL `ColumnValues` IN/NOT IN has row-level evaluation (README).
25. OpenRefine — https://openrefine.org/docs/manual/facets — BSD-3-Clause (not checked) — Text facets group identical values with counts and "do no guessing about typos or near-matches"; errors arise from transformations and can be faceted if "store error" is chosen. Reconciliation (reference lists): page not read.
26. ISO 4217 — https://en.wikipedia.org/wiki/ISO_4217 (secondary; the standard text is paywalled, SIX maintains the lists per this page) — CC BY-SA 4.0 (not checked on page) — Finding: `XTS` is reserved for testing; `XXX` is "no currency" (a transaction with no currency); `XAU XAG XPD XPT XDR` etc. are non-national; the X prefix is used because no ISO 3166 country will ever start with X. The page says nothing about unassigned codes such as `XYZ`. Page truncated at 100k of 233k chars. Whether ISO 4217 formally calls X-codes "unassigned" vs "reserved": **not checked**. `XYZ` is therefore: a well-formed code, in the user-assigned-style X range, not in any ISO list read.
27. Relevance (D): all three tools read treat a non-member value as a failed row, and Soda keeps it distinct from missing; none treats "not in the list" as a reason to guess. Row-level error reporting is normal practice. That supports writing an error row for INVALID, which the engine's own `errors` already carry (`country.py::_unresolved` sets `errors=["not a recognized ..."]`).

### Options for finding 5
Verified part: INVALID currency (XYZ) gives no error message in the app (from the task brief; not re-run here). Whether `currency.py` sets `errors` for INVALID: not read in full (only lines 1-50).
- **5a. Add the same kind of `errors=[...]` entry as `country.py::_unresolved` for INVALID currency, with a fix hint (J11): "not an ISO 4217 code; X-codes are reserved/test (XTS, XXX) or non-national".** Pros: matches the country pattern, matches GX/Soda practice, one change in the shared place. Cons: none of substance; the clone writes the row only if the error exists. Risk of a wrong value: none (value stays INVALID).
- **5b. Leave as is; make the clone write an error row for every non-NORMALIZED status.** Pros: no per-normalizer work. Cons: touches the clone's contract, error rows without text, and ADR-018 says INVALID is not queued. Risk: none, but a generic row has no reason text.
- **5c. Treat X-pattern codes specially (XTS, XXX as valid "special" ISO 4217 codes, XYZ as INVALID).** Pros: faithful to ISO 4217 (XTS and XXX are real). Cons: ISO 4217's X rules were read only second-hand; XXX/XTS being "valid" for a normalizer that feeds finance is a product decision. Risk: low.
Recommendation: **5a** (the error message is the missing piece; fix once in `currency.py`, then check `money.py` reaches it). Decide separately whether XTS/XXX are VALID (5c needs the owner).

### Open questions for the owner (finding 5)
1. Should an INVALID currency write an error row in the clone (like country), and should the text say how to fix it?
2. Are `XXX` and `XTS` valid codes for this engine? They are in ISO 4217; the data-quality meaning ("no currency", "test") differs from a currency.
3. Does `XYZ` need a different status from a misspelling like `UDS`? Both are INVALID today; no source read distinguishes them.
