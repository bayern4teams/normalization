## 1. API design: standards and comparable products

1. **RFC 9457 Problem Details for HTTP APIs** — https://www.rfc-editor.org/rfc/rfc9457.html — free IETF spec. Media type `application/problem+json`; members `type`, `title`, `status`, `detail`, `instance`; extension members allowed, clients must ignore unknown ones; generators should not expose stack dumps. Relevance: today routes raise `HTTPException(detail=str)`. Use problem+json with an extension `code` and, for AMBIGUOUS/INVALID, normal 200 results (they are results, not errors).
2. **Google AIP-151 Long-running operations** — https://google.aip.dev/151 — CC-BY design guide. Long method returns an Operation; `done`, `response`, `error`, `metadata` (progress, partial failures per GetOperation); failures that prevent starting return an immediate error; operations may expire (about 30 days rule of thumb). Cancellation is NOT on this page (AIP-151 itself; cancel is in the Operations service, not checked). Relevance: matches existing `clone-jobs` + `/start` + status; map to `202 Accepted` + `Location: /jobs/{id}` + `done` flag.
3. **IETF draft-ietf-httpapi-idempotency-key-header-08** — https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/ — active Standards Track draft, updated 2026-10-22, expires 2027-04-25, not an RFC. `Idempotency-Key` is a Structured Field String. Server SHOULD: 400 if missing (where required), 422 if reused with a different payload, 409 if the original is still in flight, same response on retry after completion. Must publish an expiry policy. Relevance: needed on `POST /clone-jobs`, `/runs`, batch submit, verdict post (a double-click today creates two jobs; not checked in code).
4. **Reconciliation Service API (OpenRefine)** — https://reconciliation-api.github.io/specs/latest/ and https://github.com/reconciliation-api/specs — W3C community-group style spec; GitHub README gave no licence and no version (not checked). The fetch of the spec page returned only its title, so endpoint details are **not verified here**. From general knowledge, not checked: a manifest at the service root, a `queries` object keyed by caller ids for batches, candidates with `score` and `match`. Relevance: the closest public precedent for "batch of values in, keyed candidates out"; copy the idea of caller-chosen keys in a batch, not the shape.
5. **OpenRefine** — https://github.com/OpenRefine/OpenRefine — BSD-3-Clause; latest release 3.10.1 (2026-03-04); pushed 2026-11-06; 722 open issues. Relevance: reference consumer of reconciliation services; shows users expect per-item match status plus a score.

Relevance: this is the upstream the repo wraps in `services/libpostal`; the repo's own HTTP service defines its contract, not an upstream standard.

## 5. Security for a LAN-only API

Repo state: `LocalCallersOnly` middleware (private/loopback client IPs only) plus `TrustedHostMiddleware`; compose publishes on one LAN address (`NORM_BIND_ADDR`) and has no authentication; no login in the UI (R10). Prior research: `docs/research/resources/_raw-local-network-only.md` (56 entries: binding, Docker firewall bypass, Host/CORS/CSRF, DNS rebinding). Not repeated here. Additions:

42. **Is auth still needed on a LAN?** Reasoning from the repo plus the prior research, not a source: the API can read and write customer databases using stored credentials (`/connections`, `/clone-jobs/{id}/start`) and can return raw values. Any device on the LAN (including a compromised one) or a browser tab doing DNS rebinding can call it. LocalCallersOnly stops other networks, not other LAN hosts. A static API key per client (one header, compared in constant time, stored hashed) is the smallest step; mTLS is stronger but needs a CA and cert handling (**not checked** for tooling). Decision for the owner (Q3 below).
43. **CORS**: with one origin (UI served by the API) no CORS headers are needed; a Python client or CLI is not a browser and ignores CORS. Keep CORS off. Do not add `allow_origins=["*"]`.
44. **Raw PII in responses and logs** — repo facts from FINAL_REPORT: `/preview`, `/field-test` and job errors return raw values; only the review route is meant to (ADR-023 R23). A single-value normalization endpoint inevitably returns the input; so make it explicit: return raw input only in the same response to the caller who sent it (echo is fine), never store it unless the result is AMBIGUOUS (queue needs it) and say so in the response; keep error bodies and log lines free of values (log a hash and a type). Source for error-detail leakage: RFC 9457 security section (entry 1).
45. **Audit log** — no source fetched. Needs: who (API key id), what route, which profile version, counts, no values. Table in the metadata Postgres (append-only). Existing verdicts already carry `decided_by` (`human:<id>` or `agent:<id>`) in `post_adjudication_verdict`; the API key id should set or check that field so callers cannot claim another identity.
46. **Docker published ports** — see prior research entries 3-8 (loopback publishing is not a firewall; CVE-2025-54388 in Engine 28.2.0 to 28.3.2).

## Gap list: today's API vs full-service use

UI calls (from `ui/src/api/client.ts` and `review.ts`): connections (list, create, delete, adhoc databases, databases, tables, columns), clone-jobs (create, verify-database, start, get, quality, errors), adjudication (queue entry, review, verdict).

A. UI actions that depend on a route that does not exist or is incomplete
1. Clone-job list for the Jobs screen: `GET /clone-jobs` exists; no filter, no pagination, no status filter (not verified whether UI uses a filter).
2. Cancel a running job: **no route** (no `/clone-jobs/{id}/cancel`). Pause/resume: none.
3. Plan amend: `PATCH /clone-jobs/{id}/plan` drops unknown keys (silent), and the UI path does not show use of it (grep of `ui/src` found no `/plan` call), so plan editing is API-only today.
4. Review screen lists all items with no server paging (R22 owner decision: "full list loads once"). For 1B rows the queue can be large: a paged/cursor route is needed for service use (UI can keep loading everything for now).
5. Verdict: single post only; no batch verdicts, no undo route seen (UI has undo; client side only? not checked).
6. Delete connection exists; no update/rename of a connection (no PUT/PATCH).
7. Destination: choosing or creating the destination database is part of create; no route to list or drop clones (cleanup after a failed run: not checked).

B. Configuration with no API (only env vars or files)
- Allowed hosts and networks (`NORM_ALLOWED_HOSTS`, `NORM_ALLOWED_NETWORKS`, address policy): env only; a bad value gives 500 on every request. Decision needed: keep as deploy-time config (recommended) but expose a read-only `GET /config` (no secrets) and validate at start-up (exit with a message).
- Worker count, chunk sizes, null-rate and type-mismatch report settings (`NORM_CLONE_*`, `NORM_SOURCE_READ_BATCH_ROWS`, `NORM_DESTINATION_INSERT_CHUNK_ROWS`): env only; per-job overrides absent.
- libpostal URL and model sha: env only.
- Dictionaries: list/create/version/rollback/delete exist; no update-in-place and no export/import (not checked).
- Profiles: create/list/get/versions/rollback/(one more POST at line 176, likely update or activate: not checked) exist, but profiles are not used by `/preview` or `/field-test` (both use `SCAFFOLD_PROFILE`); no dry-run of a profile against a sample; no diff between versions.
- Runs (`/runs`) are in-memory (`InMemoryStore`, row cap `NORM_MAX_RUN_ROWS` default 40,000), so they cannot serve a 1B-row service; they are a different, smaller path than clone jobs.

C. New capability (value + type + options)
- Single value: `/field-test` returns `NormalizedValue` but accepts only `field_name`, `semantic_type`, `error_policy`; no options object, no profile reference, no review-queue write, no locale/country hint.
- Batch: `/preview` takes a list but returns a bare list in order; no caller keys, no per-item error, no size limit stated (not checked), and it returns raw values (FINAL_REPORT).
- Long jobs: clone jobs poll via `GET /clone-jobs/{id}`; there is no generic job resource for "normalize this batch of 5M values from a file/table".
- Idempotency keys, problem+json errors, pagination, `/v1` versioning, and API-key auth: none.
- Machine-readable `/docs`: off.
- Python client and CLI: none (not checked whether a `scripts/` client exists; `ls` of root shows only `scripts/`).

## Candidate designs

**Design 1 — Minimal: extend the current FastAPI app, keep ProcessPool inside the api container.**
Add `POST /v1/normalize` (single and batch with caller keys, options, `mode=enqueue_ambiguous|dry_run`), problem+json, `/docs` self-hosted, API key, idempotency keys on job-starting POSTs; generate client with openapi-python-client plus a Typer CLI.
Pros: no new containers, no new dependency except client tooling; fastest. Cons: worker memory and api share one 4 GB cgroup (the repo measured 3.4 GB peak at 50,000 rows); api restart kills jobs (resume exists via heartbeat); fails the owner's "separate worker" decision. Risk: a heavy job slows the single-value endpoint.

**Design 2 — Recommended: api + worker containers sharing the existing metadata Postgres, queue by procrastinate (or a small SKIP LOCKED table).**
Compose services: `api` (stateless, serves UI and `/docs`), `worker` (scale with `--scale worker=N`, each with its own `mem_limit`), `postgres`. `libpostal` and all source/destination DBs live on the benchmark machine over the LAN (`NORM_LIBPOSTAL_URL` points at it; compose no longer builds libpostal on the laptop). Job resource = AIP-151-style operation (`202` + `Location`, `done`, `metadata.progress`, `error`). Cancel via procrastinate abort or the existing heartbeat/state machine.
Pros: no new infra beyond Postgres; real isolation of memory; cancel/retry/priority exist (verify priority and concurrency doc pages before commit, not verified here); one compose file. Cons: a new dependency (procrastinate, MIT, maintained; psycopg LGPL needs an owner yes), migration of clone worker from ProcessPool to a queue task, per-worker libpostal pool needed. Risk: Postgres load from NOTIFY polling is low but unmeasured; queue tables grow (needs retention).

**Design 3 — Reuse the repo's own scheme: worker container runs the existing clone loop (poll `clone_jobs` rows with SKIP LOCKED + heartbeat), no queue library.**
Pros: zero dependencies; the heartbeat and resume code already exists; smallest diff to reach "separate worker". Cons: you own retries, priorities, backoff, cancel; the batch-normalize jobs (not clone jobs) need a second table or generalization (AGENTS.md F5: one implementation). Risk: reinventing; subtle SKIP LOCKED races (docs warn of inconsistent views).

**Design 4 — Durable workflow engine (DBOS, or Temporal/Hatchet).**
Pros: strongest resume semantics, built-in queues and cancel (DBOS cancel/priority not verified here). Cons: large rewrite of `clone_executor.py` (2,723 lines), concept load; Temporal and Hatchet add servers (Hatchet has three 2026 advisories, see entry 22); too heavy for the laptop-only rule. Risk: lock-in, schedule slip. Not recommended now.

Cross-cutting choices (any design): generate OpenAPI -> openapi-python-client (pin; schema is ours) -> Typer CLI; Schemathesis in CI against a disposable stack; Starlette upgrade plus the Host regression test; remove raw values from `/preview`, `/field-test` and job errors except where the caller sent them; no streaming until a freshness requirement exists.

## Open questions for the owner

1. Auth: keep "no auth, LAN only" (ADR-022) or add a per-client API key now? Recommendation: API key (the API can read customer databases and return raw values; LAN means any LAN host).
2. Single-value endpoint and the review queue: should a plain `normalize` call ever write to the review queue, or only when the caller sets `enqueue=true`? Recommendation: opt-in flag, default off, because it stores a raw value.
3. Raw values: may `/normalize` echo the input value in the response? Recommendation: yes for single/batch (caller already has it), no in logs, job errors or any list route.
4. Dependency approval: procrastinate (MIT) and its psycopg driver (LGPL-3.0, copyleft rule F7), or Design 3 with no dependency? Also openapi-python-client, Typer and Schemathesis, each pinned.
5. `/docs`: self-host the Swagger UI assets (new vendored files, licence check needed) or serve a static page that renders from `/openapi.json`? ADR-023's CDN objection stands.
6. Versioning: put everything under `/v1` now (breaking the UI's paths, so a UI change) or add `/v1` aliases only for new routes?
7. Profiles vs `SCAFFOLD_PROFILE`: should `/normalize` accept a `profile_id` (and version) so tenants configure rules through the API, or is `semantic_type` + options enough for now?
8. Scale: at 1B rows in one database, is the target a single run or incremental re-runs? Unmeasured in the repo; a throughput test on the benchmark machine is needed before choosing worker counts.
9. Is the metadata Postgres allowed to stay on the laptop (it holds job state, queue, audit log, verdicts) given "only app containers" there? Postgres counts as an app container in this reading; confirm.
10. Idempotency window: how long to keep keys (the draft needs a published expiry policy)? Recommendation: 24 hours.
11. Jobs from files or tables: should the async batch job read values from a source table/column (already the clone path) or accept uploaded files? Uploads need size limits and storage on the laptop.
12. Webhooks: skip (polling only) for now? Recommendation: skip.
