## Findings
1. **MUST FIX (origin write path): a job stored before D14 is not refused in Phase 2.** The old `create_clone_job` stored
   `destination_connection_id == source_connection_id` and `destination_database == source_database` for `in_place`. The
   same-origin check lives only in the request validator (`schemas.py::_destination_is_not_the_origin`); the executor
   (`start_phase2`, `_run_phase2`, `verify_and_create_schema`) never compares them. After D14 such a job in SCHEMA_READY / RUNNING / FAILED
   resumes and writes to the ORIGINAL table name (no staging name any more): Postgres `bulk_insert` into the origin
   (duplicates on PK-less tables), ClickHouse `_resume_point` runs `truncate_table(origin, table)` (destroys the original).
   Probe `.handoff/D14.attack_legacy_job.py` (lint-clean, 2 passed; passing = the defect): `_run_phase2` builds the writer
   from connection `c1` (the source), and `_resume_point` truncates `("shop","orders")`. LOCAL_VERIFY only says "delete such rows".
   Fix: one shared check (same connection id and same database) in the executor, called by `verify_and_create_schema` and
   `_run_phase2`/`start_phase2` (fail the job with the "choose another database" message), and the schema validator reuse it (F2).
2. **SHOULD FIX: same server through a second saved connection is not caught.** Two saved connections with equal engine,
   host, port and database but different `connection_id` pass the validator. Postgres Phase 1 then fails only because
   `CREATE TABLE` finds the table (accident, not design); with `source_schema` set to a non-default schema it creates new tables
   in the origin database. The acceptance file chose not to guess identity; engine+host+port+database equality is provable and could be
   refused in `create_clone_job` (it holds both connection rows). If the owner wants the "no guess" reading, record it as a known limit.
3. **Stale text:** `docs/clone-e2e-guide.md:420` says "normalized-in-place values" (reads as the removed mode);
   `tests/integration/fixtures/postgres-init/01-init.sql:84-86` still explains in-place needing a writable database
   (the `writable_user` login itself is still used as the clone destination login, so keep the login, fix the comment).
   Not caught by the grep (hyphen/prose forms in a guide and an SQL comment outside the scanned paths).
