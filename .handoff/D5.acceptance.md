# D5 acceptance (derive mode): the cast gate fits the target column, on both engines

Derived from improvement-report D5 (Evidence/Fix), plan 2.4 and 9 "D5", ADR-020, LOCAL_VERIFY "D5 overflow", and the lead's finding. Not from the implementation.
File: `tests/unit/test_typed_destination_d5_acceptance.py` (marker `unit`, 479 cases, ruff check/format and mypy clean).
`tests/unit/test_typed_destinations.py` is untouched and must stay green (green today).

## Assumed API
- `storage_types.coerce(semantic_type, value, engine="postgres")` (keyword, default postgres). Test helpers pass `engine` only if `coerce` accepts it, so today's failures are real overflow failures, not TypeErrors. `test_coerce_takes_an_engine_keyword_defaulting_to_postgres` pins the name and default.
- The executor passes the engine to the per-value path: `clone_executor._apply_value` (and `_apply_column`) must take a keyword named `engine`, `dest_engine` or `destination_engine`. `_call()` in the test introspects signatures, feeds the known kwargs, and fails loudly if a new required keyword-only parameter appears. `typed_as` is taken from `_destination_plan(...)[2]`, so a changed shape of `typed_columns` values works too.
- Typed set comes from `storage_types.is_typed` over `FieldSemanticType`, limits from `sql_type()` parsed with a regex in the test (`P,S` -> max integer digits P-S; no `(P,S)` = unbounded). Nothing hand-listed except the lead's pinned ADR examples.

## Satisfiability proof
A scratch reference gate (outside the repo, `scratchpad/refplugin.py`: engine-aware coerce from the type string, plus engine-taking `_apply_value`/`_apply_column` wrappers) passes all 479 cases and `test_typed_destinations.py`. So the checks are consistent and the fix is implementable as the lead described.

## Flags for the lead (decide, or tell the verifier to relax)
1. TestPostgresHardCeiling goes beyond the ADR line "unbounded Postgres NUMERIC has no integer-digit limit". PostgreSQL docs: NUMERIC holds up to 131072 digits before the decimal point, and `Decimal("1e999999999")` is finite, so an INSERT of it still aborts the chunk. The same fact is in the `storage_types.py` comment. If you will not gate it, record a `ponytail:` ceiling and delete that class; do not leave a literal 131072 without a source note (the grep flags it).
2. Rounding carry (`99..9.99..9` with one fractional digit too many) is required to be rejected or returned in a fitting form. A pure `adjusted() >= int_digits` check fails it.
3. `0e999` (zero with a huge exponent) must not be rejected: `adjusted()` is 999 but there are no integer digits. A naive check fails it.
4. `coerce(.., 10**5000)` must not raise (`str(int)` limit). Unreachable from the executor (display is `str | None`), included because `coerce` takes `object` and the brief says never raises.
5. Not asserted (open question, not tested): fractional digits beyond the column scale (`0.00001` into MONEY rounds silently on Postgres and may truncate on ClickHouse); unknown engine names.

## Implemented, unverified (needs live data, LOCAL_VERIFY D5 overflow)
These tests prove the gate and the per-value path with fakes. They do not prove that a real ClickHouse/Postgres INSERT accepts everything the gate lets through (rounding on ClickHouse `Decimal` binding, the Postgres ceiling). Compare the live result with `SELECT count(*)` on the destination and `/errors`.
