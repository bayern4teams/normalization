## What changed
- `structured["rfc3966"]` = libphonenumber `format_number(..., RFC3966)`, always present (no-extension value is the base URI, no `;ext=`).
- `comparison` = rfc3966 iff `parsed.extension`, else E.164 (unchanged bytes). `search` stays E.164; `display` and all other structured keys unchanged.
- Region handling: the pre-parse "no region and no '+' => AMBIGUOUS" gate is replaced by "try libphonenumber with region None; if it cannot parse, AMBIGUOUS". So `tel:+<cc>...;ext=N` parses with no region (it states its country), and the emitted comparison is a fixed point. Plus-prefixed failures stay INVALID. No hand-written tables (section 2.4); the only literals added are comments.
- CONFLICT, decided toward the acceptance baseline: the baseline has `tel:+14155552671` (no ext, no region) as AMBIGUOUS, and TestNoExtensionOutputUnchanged forbids moving it. So a regionless tel:+ URI is accepted ONLY when an extension is present; otherwise it stays AMBIGUOUS. Marked `ponytail:` in phone.py (ceiling: inconsistent for ext-free tel: URIs; upgrade: delete the 2-line guard `if region is None and not has_explicit_plus and not parsed.extension`, then update the baseline row). Lead decision wanted.

## FALSEHOODS.md / FAQ.md (fetched from upstream raw.githubusercontent.com; not in the installed package)
- "Phone numbers are numbers ... or have an extension portion": keep as string, keep extension apart; leading zeros significant (rfc3966 via format_number preserves Italian-style leading zero).

- Plus sign is not optional / 00 not universal: supports the no-guess AMBIGUOUS rule.
- +1/+7 shared across countries: region comes from libphonenumber, not the calling code.
- FAQ prefix_not_removed: national prefix may remain in national_number, so the URI is produced by the library, never rebuilt by hand.
