## Notes / ambiguity in the spec (decided, flag if wrong)
- Plan says "structured byte-identical when no extension" AND "add structured['rfc3966']". Resolved: for no-extension numbers `rfc3966` may be absent, None, or the base-number URI; every other structured key must be byte-identical. With an extension it is REQUIRED.
- `tel:+<cc>...` with no region is required to parse (a global number is not ambiguous). Today it is AMBIGUOUS (the "+" check apparently misses the `tel:` prefix); this is needed for the idempotency requirement (comparison with ext is a `tel:` URI).
- `display` is expected unchanged with an extension (libphonenumber INTERNATIONAL with `ext.`).
- The attacker should still try: extension longer than 20 digits, extension with spaces/letters, `;ext=` before the number, `tel:` with `phone-context`, `;isub=`, the full-Dispatcher property idempotency.
